# ADR 0001 · 两套看板的权威与单向投影

- 状态：已接受（2026-10-15）
- 决策者：业主 + 会话 A
- 相关：`CONTEXT.md`（任务语义 / 执行事实 / 等业主），`skill/agent-collab-runbook/references/receipt-contract.md` §6

## 背景

本协作同时存在两套「看板」：

1. `<交接区>\BOARD.md`——五个列、每卡四件齐全、`LOG.md` 只追加的**文件看板**。
2. DSH 任务看板台账（`~\.dsh\task-board\ledger-v2.json`）——Host 真正执行过的卡的**执行台账**，带 `status`、`executions[]`、`sessionId`、时间戳。

两套都「能改状态」，但它们之间**没有任何同步机制**：`BOARD.md` 的列靠人手改，DSH 台账靠 Host 写。第一次全量对照就发现了真实漂移：6 张已完成但列陈旧的卡（其中一张停在 `running` 而 `executionCount=0`，是从未被运行过的死态）。同时，DSH 侧的排期/唤醒是**拉取式**、卡片的 `prompt` 在开始执行后**冻结**、两处状态互不回写。

在这个前提下，「让两套看板保持一致」有三个选项：双向同步脚本、把任务语义整体迁进 DSH 台账、或明确谁是权威并只做单向投影。

## 决策

1. **`BOARD.md` 是任务语义的唯一权威**：做什么、谁做、怎样算完成、证据是什么，只以它为准。
2. **DSH 任务看板台账是只读的执行事实附件**：它记录「哪张卡在什么时候被谁跑过」，**不写回、不同步、不进门禁**。
3. **两处不一致时以 `BOARD.md` 为准**，并在 `LOG.md` 追加一行提出改单，而不是去改台账。
4. **不建双向同步脚本**，也不把任务语义迁进台账。
5. 允许**单向投影**：把 `BOARD.md` 的卡按需映射成 DSH 卡（或反之用 `record-external-outcome` 收口历史卡），但投影永远是**一次性动作**，不是持续同步。
6. 投影动作必须在 `LOG.md` 留痕（谁、什么时候、把哪几张卡、从什么状态映到什么状态）。

## 后果

- 好处：任务的「为什么」留在可 diff、可 review、可 `git log` 的文件里；执行事实的「什么时候」由 Host 保证；两者都不必假装知道对方。
- 代价：漂移是**结构性**的，不会自愈。因此巡检卡必须固定问三个问题之一：**两套看板是否漂移**（对照 `BOARD.md` 的列与台账的 `status`），发现漂移只写 `LOG.md` 改单，不自动改。
- 不引入的新机制：同步脚本、状态镜像服务、双写事务。

## 被否决的替代方案

- **双向同步脚本**：会造出第二条真相与第二条写路径；一旦脚本出错，两处都会错，且没有哪一处能作为裁决者。
- **整体迁进 DSH 台账**：任务语义将进入一个我无法逐行 review、无法随仓库提交、无法在 PR 里讨论的存储；今天 `BOARD.md` 的最大价值恰恰是它可以被 diff 和 review。
