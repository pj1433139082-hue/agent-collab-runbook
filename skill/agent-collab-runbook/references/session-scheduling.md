# 看板做排班与唤醒

本文件回答一件事：**怎么让"到点有个会话接着干"这件事成立，以及哪些说法是不成立的。** 结论先行：只用现成能力，不自建调度器、消息总线、队列或重试引擎。

## 1. 能力边界（先认清本机有什么）

| 想要的 | 本机可用的现成能力 | 判据 / 边界 |
| --- | --- | --- |
| 按时间重复执行某张卡 | 任务看板的计划（5 字段 cron 或一次性 `once`） | 到点**开一个新会话**执行该卡；不排队、不补跑 |
| 让下一次巡检看见上一次的基线 | 卡字段 `reuseSession: true`（会话复用策略） | 复用同一会话即保留上下文；`false` 则每次新会话，没有基线可比 |
| 给已存在的卡换"敲门行" | 标签字段 `tags[].promptPrefix`（每卡 ≤200 字符，**可改**） | `title` / `description` / `prompt` 在卡开始执行后**冻结**，改不动 |
| 会话之间传事实 | 文件当信封：交接区目录（`BOARD.md` / `PLAN.md` / `LOG.md`） | 文件是唯一被双方都读得到的载体；不看聊天记录 |
| 判断"投递是否真的发生" | 会话列表里出现新的一次执行（新 `sessionId`） | **没看到新回合就是没投递成功**，不许写成"已唤醒" |

**已实测的默认行为**：一卡一次运行 = 一个新会话（同一张卡两次执行的 `sessionId` 不同）。所以"同会话内串扰"不会发生；但**隔离粒度是会话/工作区，不是文件或路径** —— 两张卡指向同一个工作区时，仍然共用同一个工作树与同一个 git 索引。这就是必须一卡一 worktree 的原因（见 `references/handoff-protocol.md`）。

**明确做不到的**（不要在这些方向上设计）：

- 任何 hook 只能在自己的生命周期内执行，不能凭空唤醒一个没有进程的会话。
- 单向"会话 → 外部程序"的通知方向相反，不能反向注入。
- 面向"正在运行的 agent server"的协议没有"空闲 CLI 会话"这个概念，也不能投递到本机回环地址（规范层面拒绝私有网段，属结构性限制）。
- 不能投给**归档会话**（宿主闸门直接拒），也不能 resume **正在跑**的会话（见下）。
**已实测可行的唤醒通道**（`dsh-cron` 的 `targetSessionId`，本机已封装）：
- **用途**：投给一个**正在空闲**的已登记会话，让它开一个新回合接着干（不是排期起新会话）。
- **前置**：`dsh-cron` 需要本地补丁把任务字段 `sessionId` 映射成 `resumeSessionId`（补丁位置 `lib/runner.js` 内 `sessionId → resumeSessionId`），否则字段传不下去。
- **入口**：`pwsh -File <交接区>\knock.ps1 -SessionId <会话id> -Card <卡号>`。
- **三条硬约束**（都实测过，违反就静默失败）：
  1. **归档会话投不进去**：宿主在 `ArchivedSessionGate` 处判据读 `ctx.workspaceRegistry.archivedSessionIds`，命中立刻 `{kind:"reject"}`，该回合以 `blocked` 结束、**消耗零 token**。投递前先查 `~\.dsh\storages\workspace.json` 的 `global.archivedSessionIds`。
  2. **正在跑的会话不能 resume**：默认拒投；`-Force` 才硬试，属例外而非常态。
  3. **回执要自己拉**：投递是单向的，干完不会通知发起方。投出去之后要自己回到该会话或看板执行记录里确认结果。
- **本机仍没有**"把消息投进一个**没有进程**的空闲会话"的一等原语；能做的是**排期起新会话**，或对**已登记且空闲**的会话按上面这条投递。

### 双看板镜像纪律（实测补写，2026-10-15）

上面"执行状态只信 Host"只说对了一半：**跨工具看板（`BOARD.md`）在任务看板上只是一份投影，而投影后没有回写通道。** 实测后果是同一张卡在看板上停在**待办态**或**运行态**、在 `BOARD.md` 里早已 Done —— 陈旧是结构产物，不是谁忘了。四条纪律：

1. **台账卡 ≠ 调度卡**：标题标了「【台账卡，非调度卡】」的卡由既有会话执行，**不该被排期**，也别指望看板替它推进。
2. **台账卡不写中途态**：建卡时状态直接写终态（"已完成 / 进行中"），**不要留**在待办/运行那两列里 —— 它们不会自己前进。
3. **换列必回写**：`BOARD.md` 改了列，必须同一次操作里把看板卡也改掉。工具语义要记清：`record-external-outcome` 是"写终止列 + 一条 `external: true` 执行记录"的正规做法；`settle` 只用于**有未结算执行**的卡死；`archive` 对**已归档卡**、`settle` 对**无未结算执行**的卡一律 `refused`，这不是报错。三者都**只动 Host 账本**，不碰仓库、不碰交接区。
4. **定期对账**：把「看板各列计数」与「`BOARD.md` 各段卡数」对一遍，差异记进 `LOG.md`。实测过一次：23 张里 6 张是陈旧的投影，另有一张只存在于 `BOARD.md`、看板上没有。

## 2. 排班的三个动作

```text
# ① 定义一张巡检卡（概念字段，实际在 GUI 或看板 API 上填）
负责人=监督会话    reuseSession=true    计划=<cron>    占用文件=无（只写 LOG.md 一行）
tags[].promptPrefix = "先跑 <交接区>\\status.ps1，再按 LOG.md 末尾 10 行判断有没有变化；只追加一行，不动仓库文件。"

# ② 定义一张采集卡（一次性收集，不需要基线）
reuseSession=false   计划=<cron 或 once>

# ③ 排期到点后，会话第一件事固定是恢复事实
& "<交接区>\status.ps1"
```

- **停机即跳过**：看板的定时执行在 Host 不运行时不会补跑（现有语义：missed occurrences are skipped, never queued）。因此**不要**写"补跑脚本"，也**不要**把"没跑"当成任务失败——它是没发生，如实报"未执行"。
- **跨会话投递的判定线**：设一个指向空闲会话的定时触发，到点后该会话真的开了新回合（会话列表里能看到新的执行记录）。看到新回合 = 投递成立；看不到 = 未投递。把这条当验收判据，而不是凭"我设了定时"推断成功。
- **静默失败要记账**：到点没动静就在 `LOG.md` 追加一行"未执行 + 时间 + 原因未知"，让下一个人看到。

## 3. `promptPrefix` 是唯一的常驻旋钮

- 卡的 `prompt` 在开始执行后冻结，所以**不要把会变的状态写进 `prompt`**（比如"当前进度 3/9"）。可变内容只有两个去处：`tags[].promptPrefix`（≤200 字符）或交接区文件。
- 200 字符装不下协议，所以 `promptPrefix` 只写**指路**的一句话："先跑 status.ps1，按 PLAN.md 的占用列确认没冲突，再干活"。真正的规矩放交接区文件与技能 reference。
- 已有的旧会话不会因为改了 `promptPrefix` 而改变常驻指令；它影响的是**之后新建/新建回合**的提示词。所以改完要记一笔"从哪一次运行开始生效"。

## 4. 文件当信封：怎么写怎么读

| 文件 | 管什么 | 谁写 | 副本权威 |
| --- | --- | --- | --- |
| `BOARD.md` | 做什么、谁做、判据 | 任何人（只写自己那行卡） | 任务语义的权威 |
| `PLAN.md` | 谁占了什么、交接点 | 各自只写自己那一行 | 占用与交接的权威 |
| `LOG.md` | 发生过什么 | 所有人只追加 | 历史的唯一账本 |
| 看板执行记录 | 跑到哪了（状态） | 只有 Host 写 | 执行状态的权威 |

**执行状态归 Host，看板是它的投影**：`BOARD.md` 只留"做什么/谁做/判据"，不把执行状态当权威。但**投影没有回写通道**，所以"不写状态就不会漂移"是错的——实测里正是这么漂的。正确的落法是：`BOARD.md` 的「状态」行照写（人要看得见），**换列时同一次操作把看板卡一起改掉**，并按 §1末尾的镜像纪律定期对账。若发现同一张卡在两处状态不一致：在 `LOG.md` 追加一行指出，把 `BOARD.md` 那格改到与看板执行记录一致，不要试图双向同步。

## 5. 明确不做

自建消息总线、持久队列、重试引擎、审计、策略引擎；不引入 Temporal / Airflow / Prefect / LangGraph / CrewAI 作为控制面；不写"看板同步脚本"。

理由：现有的通用编排没有一个同时理解"占用文件"和"验收判据"这两件本领域的事；把一次非确定性的 LLM 会话塞进工作流引擎，等于把主体搬进 Activity，只剩一层昂贵外壳，代价是常驻服务、确定性约束和一个新的失败面。真正需要自建的只有**一层薄薄的约定**：卡片模板 + 单向投影 + 巡检循环——也就是本技能。
